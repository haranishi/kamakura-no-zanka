# Design: 刃の軌跡で振りを読ませ、突きと二段目の当たりを振りに合わせる（8.3a）

本人の評価（2026-10-30「戦闘シーンに迫力がない。まだまだ」）への最初の手当て。振りの向きと速さが読めないことと、当たりと振りがずれる2技を、表示だけで直す。
`combat.js` の規則（時間割・ダメージ・構え・間合い・無敵・連続入力）と時間の進み（命中の停止の長さ・倍率）は変えない（R18.9）。実座標のノックバック、音の作り直し（7.7）、握り（8.6）、木も対象外。
要件は requirements-polish3.md の R18.2〜18.5・18.9 で、上位の設計は design-combat-presentation.md にある。タスクは tasks-polish3.md の 8.3a。
数値は2026-10-30の実測（M4 Pro・Chrome・1280×720・DPR1・seed 1333）。

## 実測：振りは速いが、刃が細い線でしか見えず、2技は当たりと振りがずれていた

実ゲームで技ごとに、刀の根元・切先・右手首の位置を毎コマ記録した（`tools/scenarios/measure-combat-trail.mjs`）。

- 切先の最大の速さは23〜47m/秒、1コマの最大移動は0.39〜0.79m。帯を出す区間（判定の0.04秒前〜戻りの始めの0.1秒後）の切先の道のりは1.7〜4.7m。刃は幅3cmの線なので、この動きがほとんど画面に残らない。
- 動作の切り出しを静的に計算すると、突き（soldier_thrust）は山（手首の速さの山）の始めが判定の始めより0.367秒早く、侍大将の二段目（officer_b）は山の終わりが判定の終わりより0.180秒遅い。実ブラウザでも、二段目は判定が終わってから0.238秒、手首が速いままだった。ほかの11技のずれは0〜29msで、直す対象にしない。
- 原因は動作の予備の短さ。突きは山まで0.2秒しかない動作を0.7秒の予備に合わせて全体を0.6倍で流し、二段目は0.267秒の予備を0.4秒に合わせて0.668倍で流していた。1つの速さでは、山の始めと終わりの両方を判定に合わせられない。
- 突きの「山」は前への伸び（手首が最も前に出る0.30秒）を挟む区間で、その間に切先は横へ約0.8m動く。刃の軸の向きに滑る突きではない。
- 予兆の金色の光の粒は、振りが始まったあとも出続け、敵の刃より明るかった。
- 弾きの火花は向きを持たず、放射状に散っていた。三段目（light3）は規則では強い技なのに、当たりの火花・音・揺れは通常の扱いだった。
- 弱二・三段目の始めは、前の技からの混ぜで切先が1コマに1.0〜1.2m跳ぶ（既存。今回は直さず、帯の区間をその後ろから始めて拾わない）。

## 採った方式

帯は、刃の内側の点と切先を毎コマ記録し、時刻で接線を割る3次エルミート曲線でつなぎ、1つのメッシュに並べる（`slash-trail.js` が純粋な部分、`fx.js` の `SlashTrails` が描画）。時刻はゲーム内の秒なので、命中の停止中は帯も止まり、引き伸びない。新しいサンプルが前から1/120秒未満なら、先頭の位置だけを置き換える。
見た目は、主人公が生成りの淡い光で、三段目と強斬り・とどめ・闇討ちは長く幅広く濃く、尾に朱をさす。敵は薄墨の弱い帯。濃さは切先側の縁の速さで付け、遅い刃はほとんど残さない。幅の向きは、切先の道の少し内側が最も濃く、根元側へ溶ける。
敵の予兆の光と帯は、時機・色・形で分ける。時機は「予兆は振る前、帯は振っている間」。予兆の光の粒は予備を抜けたら足さない（中断された技の光もすぐ止まる）。色は金色と薄墨、形は刃に沿う点と、刃の後ろに掃いた帯。
三段目は、停止の長さ（0.07秒）をそのままにして、振りと当たりの音・火花・揺れ・視野だけを強い側へ寄せる。揺れ0の設定では揺れも視野も0のまま。
弾きでは、相手の切先が直前に動いた速度を帯から取り、火花を入射の向きへ偏らせる（粒は前と同じ22）。速度が無ければ、相手から受け手への水平の向きを使う。
突きと二段目は、使う区間（from・to）を変えずに、予備・振り・戻りの3区間で速さを変えて、山の中央を判定の区間の中央へ置く（`anim-data.js` の `MOVE_SYNC`・`syncedSegment`）。振りの速さの上限は1.8倍。この2技は論理と同じ時刻で動作を進め、敵の個体差（0.94〜1.06倍）を掛けない。

## 捨てた案と理由

| 案 | 捨てた理由 |
| --- | --- |
| 加算合成の帯 | 設計の条件どおり、白飛びと、予兆の金色が埋もれる危険がある。通常の半透明で足りた |
| 敵の帯を濃い墨にする | 撮影で、林の暗がりでは消え、明るい所でも予兆の光の陰に埋もれた |
| 突きだけカメラへ向けた細い線にする | この突きは切先が横へ動くので刃の帯で読める。描き方を2つ持つ複雑さに見合わない |
| 1つの速さで突きを合わせる | 0.29倍になり、突き自体が0.8秒かかる遅い押し出しになる |
| 予備の初めで動作を止めて待つ | 固まった姿勢が続く。3区間の速さのほうが「溜めて突く」に見える |
| 範囲を指定してGPUへ送る | three.js が毎回小さな物を作る。全体でも約47KBなので丸ごと送る |
| 帯を当たり判定に使う | 規則を見せ方に依存させない（design.md の判断を継承） |

純粋な部分の試験14件と変異試験30件（すべて検出）、切り出しの試験4件と記録の試験12件。実ブラウザの毎コマの確かめは `tools/scenarios/regress-slash-trail.mjs`。

性能は、測った時刻に別の作業のビルドとブラウザが動いていた（load average 12〜16）。別プロセスの8試行（帯あり・なしを交互）でもp95は17.9〜31.1msと揺れ、帯あり・なしの差より揺れのほうが大きい。
そこで同じページの中で、帯あり・なしを150コマずつ交互に各1500コマ測った。中央値14.5/14.7ms・平均15.8/17.1msで、帯ありが遅いという差は見えなかった。描画呼出は最大で682→683、三角形は最大で56増えた。
変更前に静かな時刻で測った標準の戦闘2回は、p95が15.8/17.2msだった。静かな時刻に全8試行を測り直すことは残件（tasks-polish3.md 8.3a）。

## 未確認と次の候補

本人のプレイ、別役の盲検採点、Safari・Firefox・実機、帯の色と長さの好みは未確認。敵の突きの帯は、横から見ると刃の動きがカメラへ向くので薄い。
次の候補は、三連の2・3段目が始まるコマで切先が跳ぶこと（混ぜの0.06秒）と、弾いた瞬間に相手の刃が高い所にある（接点と火花の位置が離れる）こと。どちらも 8.3 の残りか 8.4 で扱う。
