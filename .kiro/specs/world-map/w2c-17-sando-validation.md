# W2c-17b 参道：鳥居や門から堂まで、敷石の道と灯籠の列が続く

寺社の門・鳥居から堂の正面まで、参道の線を施設の並びから導き、踏み固めた土の道・切石の敷石・両側の灯籠を出す。
実 Chrome で、八幡宮の赤い鳥居から堂へ向かう敷石と、大仏殿の門から大仏へ続く敷石を確認した。`&sando=0` で元の画に戻る。
全試験は、私有データあり 1,676 件成功・失敗 0。`npm run check` 成功。

## 実 Chrome で分かって直したこと

- 最初の色（明るい灰）は、昼の日なたで白いタイルに見えた。暗めの、少し暖かい灰にし、1 枚ごとの明るさの差を広げた。
- 灯籠を 14m おきに並べると、置き換える前の規則（門から堂まで）より数が減った。10m おきにし、長さが足りる参道には 2 対以上を置く。
- 人工の世界（CI 用）に門を足したので、施設の数を 1 に固定していた既存の試験 1 件を、堂を探して確かめる形に直した。
- 敷石は 1 メッシュ・1 描画命令（1 枚 28 三角形・上限 9,000 枚）。速さの差は測っていない。

## 既知の制約

- 参道ができるのは、門や鳥居と堂の両方が歩ける範囲にあり、間を塀の帯・水・急斜面・家に遮られない寺社だけ。山の中腹の寺には、まだ出ない。
- 石段の上には敷かない（石段は別の部品）。敷石に当たり判定は無い（地面と同じ高さなので、歩くと少し沈んで見える）。
- 八幡宮の参道は、鳥居から堂までの短い区間。浜から続く大通り（若宮大路）は、道のデータの側で扱う。

## 依頼を引き継いだ範囲と判断

仕様は共通依頼書とSANDO依頼書のS1〜S3。WW13の道路・小物の仕組みを継承した。
追加の仕様ファイルは作らず、この記録に判断と検証をまとめる。
順序は、線の導出と読み込み → 道への合成 → 敷石 → 灯籠 → 検証。

敷石の長辺を進行方向の約0.9mにし、短辺は道幅の中央6割を3〜4列に収めた。
寸法の揺らぎを目地へ押し出さないため、回転後の外接幅と奥行きを使って間隔を取る。
描画の上限は敷石1命令の追加で12→13。敷石は既存小物の6万三角形枠と別にした。
同じ枠に入れると、足元の敷石が灯籠や既存小物を押し出すため。上界は9,000枚×28三角形。
既存の7種類を検査する試験は維持し、参道のない人工世界では敷石0枚も明示して検査する。

## 親が実Chromeで確かめる手順

1. 親の環境で私有世界を指定して既存サーバーを立て、1920×1080で開く。
   `/valley/index.html?world=kamakura&debug=1&pos=-366,230&yaw=0&time=noon`
2. `__kzProps().ready`を待ち、`visible.paver`と`nearestSando`の距離・北から時計回りの方位を見る。
   その方向へ歩き、鳥居から堂への線・土の縁・灯籠の列・石段に板がないことを確かめる。
3. 同じ位置に`&propsdebug=1`を足す。紫色の板と間欠的な柱が敷石の線。
   20m先で線が40画素以上見えるかを数え、通常色へ戻して白飛びと影を確認する。
4. 大仏殿は`&pos=-2200,-700`でも確認する。堂や門の箱の中へ板が入っていないか見る。
5. 同じ位置・向き・時刻のまま、通常／`&sando=0`／`&props=0`を固定画角で撮る。
   sando=0は従来の地面と小物配置へ戻る。props=0は板と灯籠が消え、土の道が残る。
6. 夕方の火、軽量、品質段階2〜3、260m付近の縮小、60m移動時のちらつきも確かめる。

既知の残件は、上記の既存試験1件。実画面の連続性・既存施設の地面との重なり・白飛び・速度は未確認。
次の最小ステップは、親がCI試験の固定値を施設データの件数へ合わせ、同じ画角で前後を撮ること。
commit・push・ブラウザ起動・外部素材や依存の追加は行っていない。
