# W2c-5c 足元の草の実装引き渡し

BRIEF-W2C5C.mdの確定済み設計を引き継ぎ、実装とNode検証を行った。
commit・pushはしていない。実機の見た目・撮影・性能は親の担当として残す。

## 採用した設計と理由

- 谷の草の描画、距離、品質、風、影、GRASSの設定を再利用した。
- 96m四方・1m升の窓を、中心から24mの移動で作り直す。
  準備中は古いfieldを保持し、完了後に参照を一括で切り替える。
- grass-view.jsにsetFieldを追加した。両窓の内側にある区画は保持する。
  縁に掛かる区画のみ既存のプールに戻すため、窓ごとの材質・画像の再生成を避けられる。
- setDensityScaleも追加した。段階2はハッシュで約0.6倍、段階3はgroupを非表示にする。
  品質変更で形・材質を作り直さず、復帰時に元の密度へ戻せる。
- 足音のクラス変換は砂と砂利、田と泥をまとめるので、元のクラスを読む口を別に足した。
  足音の重み・川のwaterAt=0.4・衝突の規則は変更していない。
- 家・施設・幹は衝突の索引、道は既存の植生用索引を再利用する。
  非表示比較の家・施設も除外する。根の散らばりを考慮し、禁止域を升の半対角だけ広げる。
- 窓の外側6mで近景・中景とも密度を落とす。元の値は別配列に保持し、重複升を再評価しない。
- 谷のmidPatchの窓全体での平均・最大による正規化は、窓を動かすと同じ升が変わる。
  鎌倉では同じ2周波の式を理論上の範囲で正規化した（1±0.8）。谷は変更していない。
- 生の升の値は世界座標だけで決まる。表示用の外周の減衰だけは窓の位置による。
- 草の窓の準備予算は標準2ms・軽量1.5ms。既存の草の区画生成予算は別に掛かる。

## 親の実機確認（メイン・2026-11-07）

結論：実 Chrome で、足元の草は見た目・窓の切り替わり・軽さとも合格。ただし見つけた不具合2件を直した。
試験は私有データなしで1,022成功・11省略、v0.9指定で1,033成功・省略0。`npm run check`・`npm run smoke`・`check-kamakura`・`git diff --check` も成功（smoke は親の環境では通る）。

### 直したこと

1. **出発点の周りに草のない丸い禿げ**：設計（出発点の周り3mは除く）どおりに実装されていたが、実機では主人公が円形の空き地の真ん中に立ち、不自然だった。草は何も妨げないので、出発点の除外を外した（`grassExclusions` と `buildKamakuraGrass` から `spawn` 引数を外し、試験は「出発点は除外しない」に変えた）。木の出発点の除外は変えていない。
2. **遅い端末で走ると、草の窓の準備が間に合わず草が足元から消える**：CPU を6倍遅くして20秒走ると、次の窓の準備に7.3秒かかり、その間にカメラが古い窓の外へ出て、近景の草が25,000枚から116枚まで減った（約3秒の草なし）。原因は草の升の作成時間の大半が「川までの距離」の問い合わせだったこと（1升で2回・文字列のキーと集合を使い、1回約18µs）。直し：
   - `createRiverIndex`（`kamakura-surface.js`）を数値のキーと検索ごとの印に作り替え、第3引数 `reach` を足した（`reach` 以内なら正確な距離・それより遠ければ「遠い」とだけ分かる値を返し、探索を打ち切る。省略時は従来どおり常に正確）。
   - 地形の川の索引を32m の升にし、`waterAt` は自分の升だけ調べる（`reach=0`）。主人公の移動が毎コマ呼ぶ経路も軽くなる。
   - 草の升は `reach=25`（除外1.7m と岸の帯25m だけ要る）。
   - 結果（Node・私有v0.9・1升あたり）：草地 34.6→1.1µs・林床 14.8→0.9µs・浜 6.4→1.7µs・川 18.9→1.8µs。私有データの草の試験は3.29秒→0.68秒。
   - 結果（実 Chrome・CPU6倍・走る20秒）：窓の準備は7.3秒→0.4〜0.6秒。草の枚数は切り替えの前後で連続（1コマで減った最大は5.8%）。
   - 川の距離は総当たりと一致する試験（32m・16m・64m・256m の升・`reach` 0／1.7／25／300）を `kamakura-surface.test.mjs` に足した。

### 実機で確かめたこと

- **見た目**（同じ画角で草あり・なし）：草地（背の高い草と草むら）・林床（シダ）・浜と川岸（ススキと低い草）・出発点・夕方（逆光で光る）・軽量（`&q=light`・まばら）・段階2（薄い）。林床は暗い影の中なのでシダは小さく見える。家・施設・道・川の中には出ない。飛行から降りた直後も足元に出る。
- **軽さ**（この Mac・ヘッドレス Chrome・制限解除・1280×720・草あり／なし）：止まっているとき 出発点 338／348fps・草地 303／314・林床 301／314・浜 317／325（1コマ約+0.1〜0.3ms）。描画命令と三角形（草地）は 388→425・1.23M→1.37M、林床は 477→493・1.79M→1.80M。
- **スマホ相当**（390×844・タッチ・CPU6倍）：止まっているとき p50 22.6／22.6／24.8ms（草なし 21.9／23.7／25.0）。歩いたときの最大 58／45.6／35.1ms（草なし 61.1／46.1／51.3）。起動直後の最大の引っかかりは草あり156・111ms／草なし96・102ms（誤差の範囲）。
- **窓の切り替わり**（走って125m・4か所・CPU通常）：各5回切り替わり、切り替わりの前後で近景の草の枚数が落ちない。1コマの作業は最大2.3ms。コマ時間の最大は9〜16ms。
- **自動画質**：段階2で近景25,310→15,260枚（×0.60）・中景2,727→1,594株（×0.58）。段階3で草の group が非表示になり描画命令が422→336。負荷を戻すと 3→2→1→0 と順に草が元の枚数へ戻る。
- **回帰**：川の中で5秒歩いて15.0m 進み足音14（両向き）。音（解錠・足音・休止・ミュート・`&audio=0`／`&mute=1`）は6c の記録と同じ数字。谷とタイトル画面・庭はコンソールが空で起動。飛行の往復（F・M・G）も動く。

### 未確認・残す点

- 実スマホの GPU・メモリ・長く歩いたあとのメモリは未測定（スマホの測定は本人の判断で後にする）。最終判定は本人が歩いて行う。
- 高い高度の飛行中も窓は追従する（見えない高さなので無駄な CPU だが、開発用の飛行なので許容。必要なら一定の高さ以上で止める）。
- 段階2の間引きは、シェーダーの距離による消え方と同じ乱数を使うため、遠くの草の消え始めが少し早くなる。
- CPU6倍で走り続けると窓が0.4〜0.6秒遅れる。遠い中景の草が一瞬薄くなる可能性は残るが、近景（8m）は保たれる。
- 田・岩・石・砂利・泥には草を置かない（設計どおり）。
