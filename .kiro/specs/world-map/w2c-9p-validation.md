# W2c-9p：起動の同期処理を縮小

家のテクスチャは元のバイト列を保って生成を短縮した。
草は近い窓だけを同期で用意し、外側と魚の索引を初回描画後に分割する。
実Chromeの起動目標と草の全域表示0.3秒は未確認。下記のNode計測だけでは合格としない。

## 採った設計

- 承認済みBRIEF-W2C9Pと既存world-map仕様を継承。見た目・配置・数・保存を変えない。
- 元のsinハッシュをFloat64の格子へ一度だけ保存。整数ハッシュへの変更より、画素を完全に保てる方法を選んだ。
- 石の候補・板の列情報も再利用する。生成は従来どおり8msで譲る。
- 家と施設は不変のCPU画素を共有し、DataTextureの所有・破棄は各呼び出し元に残す。
- 環境値は必要な世界座標の升を遅延生成し、窓の世代内で共有する。法線は近景の要求時だけ計算する。
- 衝突格子の候補を8m単位で共有し、同じコライダーの重複評価を除く。
- 草の25mの川距離を環境の15m帯にも渡す。isSeaがある地形では、川の除外と重複するwaterAtの照会も省く。
- 通常は120m四方（片側約60m）、軽量は96m四方を同期warmする。
  外側は2ms／軽量1.5msのタイマーと更新で準備し、元の352m／256m窓へ一度だけ拡張する。
  完成まで近景は残す。共有する内側の描画資源は維持し、境界だけ既存のプールで交換する。
- 魚は空のグループで起動し、初回描画を挟んで2msずつ索引を作る。
  生息不可が確定した候補の残りの照会は打ち切る。経路の計算式は維持する。
- GLSL、海関連の配線、共用の谷・庭ファイルは変更していない。追加URL指定なし。

## 検証

- 元のテクスチャのSHA-256を3条件で固定し、完全一致を確認。9g3の統計・周期試験も維持。
- 小さい窓から拡張した全セル・端の値・高さを、元の大きい窓の一括生成と比較。
- 偽の時計とスケジューラーで、完成前の草・操作、完成後の一度の交換、破棄時の取消を確認。
- 魚の準備前の操作、分割後の経路一致、資源の各1回の破棄を確認。
- 関連60試験：私有データなし54成功・6スキップ、あり60成功・失敗なし。
- 全体`npm test`：1,102成功・20スキップ・1失敗。私有あり：1,122成功・1失敗。
  失敗は担当外の`kamakura-shore-9e2.test.mjs:65`（2 !== 1）。1分以上後の単独再実行でも同じ失敗。
  該当ファイルは変更していない。
- `npm run check`：私有データなし／ありとも成功。
- `npm run smoke`：開始前／終了後とも`listen EPERM 127.0.0.1`。ブラウザ到達前の環境制限。
- 日本語記録はnatural-japaneseのクイック検査を実施。文長の均一性1指摘は測定記録のため保持。

## 親が実機で確認する手順

1. `?world=kamakura`を開き、「準備できた」までを計測する。
2. 同じURLに`&gdetail=0&gsoil=0&htex=0&ftex=0&seav=0&fx=0&fish=0&glook=0&sea=0`を付けて比較。
   目標は磨き込み前＋0.5秒以内。Nodeの値からこの合格を推定しない。
3. 起動直後から歩き、近景の草が残り、外側・魚が一度だけ現れるか確認する。
   約0.3秒時点の全域の草、家の模様・色・位置・数、ちらつきも確認する。
4. `&q=light`と390×844・CPU6倍でも同じ確認を行う。

ブラウザは依頼条件により実行していない。画素のGPU描画、FPS、GPUコンパイル、音は未確認。
